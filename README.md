# دژاوو | DEZHAWO

نسخهٔ PHP فروشگاه دژاوو برای هاست **cPanel با PHP و MySQL/MariaDB**. محصولات، موجودی، فروش حضوری، سفارش‌ها، کاربران و تیکت‌ها در دیتابیس مشترک ذخیره می‌شوند. **phpMyAdmin ابزار مدیریت و واردکردن دیتابیس است**؛ سایت با PDO به MySQL متصل می‌شود.

روی هاست به Node.js، npm، Composer یا مرحلهٔ build نیاز نیست. نسخهٔ قبلی HTML فقط نمونهٔ نمایشی بود؛ برای فروش و انبار مشترک، این نسخهٔ PHP را نصب کنید.

آدرس فایل‌های JavaScript و CSS بر اساس محتوای همان فایل نسخه‌بندی می‌شود. پس از آپلود نسخهٔ جدید، مرورگر آدرس تازهٔ فایل تغییرکرده را دریافت می‌کند تا فایل قدیمیِ کش‌شده با امکانات جدید مانند دکمهٔ ارتقای دیتابیس مخلوط نشود. هنگام به‌روزرسانی، فایل‌های PHP و پوشهٔ `assets` را کامل منتقل و تنظیمات خصوصی و عکس‌های فعلی را حفظ کنید.

ظاهر فروشگاه و پنل مدیریت به‌صورت پیش‌فرض از تنظیم روشن یا تاریک سیستم پیروی می‌کند. دکمهٔ نمایش در هدر و پنل، سه انتخاب «سیستم»، «روشن» و «تاریک» دارد؛ انتخاب دستی در همان مرورگر حفظ می‌شود. برای افزودن این قابلیت به نصب موجود، فایل‌های برنامه را به‌روزرسانی کنید؛ تغییر یا واردکردن دوبارهٔ دیتابیس لازم نیست.

صفحهٔ فروشگاه به ظاهر نسخهٔ اول برگشته است: زمینهٔ کرم، رنگ‌های قرمز و زرد و آبی، ویترین متحرک، دسته‌بندی‌ها و داستان دژاوو. تم سیستم/روشن/تاریک، ورود پیامکی، بنر اقساط و روش‌های پرداخت حفظ شده‌اند.

محصولات عکس واقعی دارند: از **مدیریت → محصولات → ایجاد یا ویرایش محصول → عکس واقعی محصول** فایل را از گوشی یا کامپیوتر انتخاب کنید. عکس با ذخیرهٔ محصول بارگذاری می‌شود و در فهرست، جزئیات کالا، سبد خرید و ویترین اصلی نمایش داده می‌شود. محصول بدون عکس با جای خالی مشخص نمایش داده می‌شود؛ تصویر ساختگی به جای عکس کالا قرار نمی‌گیرد.

در **مدیریت → دسته‌بندی‌ها** دستهٔ اصلی یا زیرشاخه بسازید، نام و والد آن را ویرایش کنید و ترتیب نمایش را تغییر دهید؛ مثلاً **قاب ← سامسونگ ← سری S** و **قاب ← آیفون**. در فرم محصول، مسیر کامل دسته قابل انتخاب است. انتخاب دستهٔ مادر در فروشگاه، محصولات تمام زیرشاخه‌های آن را هم نشان می‌دهد. غیرفعال‌کردن دسته، شاخه‌های زیر آن را از فروشگاه پنهان می‌کند؛ حذف دستهٔ دارای محصول یا زیردسته تا انتقال وابستگی‌ها مجاز نیست. نوع فیزیکی یا دیجیتال از والد گرفته می‌شود؛ شاخهٔ دارای محصول بین این دو نوع جابه‌جا نمی‌شود. دسترسی‌های مستقل `categories.view` و `categories.edit` در بخش نقش‌ها قابل تخصیص‌اند.

**ارتقای دیتابیس از داخل سایت:** پس از آپلود فایل‌های نسخهٔ جدید، با حساب مدیر اصلی وارد شوید. اگر ساختار دیتابیس به تغییر نیاز داشته باشد، بالای سایت اعلان و دکمهٔ **«ارتقای دیتابیس»** نمایش داده می‌شود. با یک بار کلیک، فقط ارتقاهای شناخته‌شدهٔ همراه برنامه اجرا می‌شوند؛ نتیجه یا خطا همان‌جا نوشته می‌شود و بعد از تکمیل، اعلان کنار می‌رود. مشتری و نقش‌های دیگر این دکمه را ندارند. تغییرات پرداخت، عکس محصول و دسته‌بندی‌ها از این مسیر پشتیبانی می‌شوند.

فرم‌های ایجاد محصول، دسته، روش ارسال و نقش پس از ذخیرهٔ موفق بسته می‌شوند. خطا در همان فرم نمایش داده می‌شود و مقادیر واردشده باقی می‌مانند. قیمت پایه، خرید، قیمت هر رنگ و هزینهٔ ارسال هنگام تایپ یا چسباندن اعداد فارسی/عربی/انگلیسی، جداکنندهٔ سه‌رقمی می‌گیرند؛ مقدار ارسالی به سرور عدد است. قیمت و موجودی محصول جدید خالی‌اند؛ صفرهای واقعیِ محصول موجود هنگام ویرایش حفظ می‌شوند. قیمت پایه و موجودی هر گزینه باید وارد شوند و قیمت خرید یا قیمت اختصاصی هر رنگ اختیاری است.

ورود مدیر، کارکنان و مشتریان **یک فرم مشترک با شماره موبایل و کد تأیید پیامکی** دارد. دسترسی پنل از نقش ذخیره‌شدهٔ همان حساب تعیین می‌شود؛ شمارهٔ جدید در ورود پیامکی فقط حساب مشتری می‌سازد. تا آماده‌شدن سرویس پیامک، مالک می‌تواند از ورود موقتِ محدود به شماره و هش رمز تنظیم‌شده روی سرور استفاده کند؛ این روش برای شماره‌های دیگر فعال نمی‌شود.

در **مدیریت → ویترین صفحه اول** می‌توانید حداکثر ۹ محصول فعال را به ترتیب انتخاب کنید. عکس، نام، قیمت و وضعیت محصول در ویترین متحرک نمایش داده می‌شود و کلیک روی آن صفحهٔ همان کالا را باز می‌کند. خالی‌کردن انتخاب‌ها ظاهر تصویری اولیه را برمی‌گرداند.

هر کالا صفحهٔ مستقل `product.php?id=...` با محتوای سمت سرور، عنوان، توضیحات، canonical، Open Graph و اطلاعات ساختاریافتهٔ محصول و قیمت دارد. لینک کالاها در HTML اولیهٔ صفحهٔ اصلی هم وجود دارد. `sitemap.xml` و `robots.txt` به‌صورت پویا ساخته می‌شوند؛ محصولات غیرفعال از صفحات عمومی و نقشهٔ سایت کنار گذاشته می‌شوند. قیمت نمایش تومان است و در دادهٔ استاندارد سئو به ریال تبدیل می‌شود. برای معرفی نقشهٔ سایت در Search Console از `https://dpsshop.ir/sitemap.xml` استفاده کنید؛ این قابلیت‌ها به معنی ثبت یا رتبهٔ تضمینی در موتور جست‌وجو نیستند.

## نیازهای هاست

- PHP **۸٫۲ یا بالاتر**؛ افزونه‌های `pdo_mysql`، `curl`، `mbstring` و `fileinfo` فعال باشند.
- MySQL **۵٫۷ یا بالاتر** یا MariaDB **۱۰٫۴ یا بالاتر** با InnoDB و `utf8mb4`.
- Apache یا LiteSpeed با پشتیبانی از `.htaccess` و اتصال **HTTPS** معتبر.
- دسترسی خروجی HTTPS هاست به سرویس پیامک انتخاب‌شده (نیازپرداز یا کاوه‌نگار) و درگاه‌های فعال زرین‌پال/دیجی‌پی، پس از تهیهٔ حساب سرویس‌ها.
- قابلیت نگهداری session در PHP. برای نصب، فایل‌ها نیازی به دسترسی نوشتن عمومی ندارند.

## نصب روی cPanel

### ۱. فایل‌های کامل پروژه

**نسخهٔ آمادهٔ `dpsshop.ir`:** به درخواست مالک، فایل `app/config.php` با تنظیمات دیتابیس اعلام‌شده همراه این مخزن خصوصی قرار گرفته است. برای دریافت کل پروژه، از **Code → Download ZIP** استفاده کنید؛ پوشهٔ داخل ZIP را باز کنید و محتویات آن را در `public_html` بریزید. فایل تنظیمات را روی هاست نگه دارید. اتصال واقعی دیتابیس از این محیط بررسی نشده است؛ اطلاعات پیامک و درگاه‌های پرداخت نیز باید جداگانه تکمیل شوند.

از بستهٔ آمادهٔ `dezhawo-cpanel.zip` یا فایل‌های همین مخزن استفاده کنید. در **File Manager → public_html** آپلود و Extract کنید؛ فایل `index.php` باید مستقیم در پوشهٔ مقصد قرار بگیرد. نمایش فایل‌های مخفی را فعال کنید تا `.htaccess` هم کپی شود.

اگر سایت در پوشهٔ `/shop` نصب می‌شود، همهٔ فایل‌ها را داخل `public_html/shop` بریزید. نصب در زیردایرکتوری پشتیبانی می‌شود؛ مقدار `app.base_url` را هم `https://your-domain.example/shop` قرار دهید.

اگر قبلاً نسخهٔ نمایشی داشتید، `index.html` قدیمی را ابتدا در محل خصوصی خارج از `public_html` پشتیبان بگیرید و از محل عمومی حذف کنید. پوشه یا فایل خصوصیِ تنظیمات نسخهٔ قبلی را بدون بررسی بازنویسی نکنید.

### ۲. PHP و HTTPS

در **MultiPHP Manager** یا **Select PHP Version** نسخه را انتخاب و افزونه‌ها را فعال کنید. از **SSL/TLS Status** گواهی دامنه را فعال کنید. سایت و نصب‌کننده را فقط با `https://` باز کنید. روی هاست واقعی، `app.env` باید `production` و `session.secure` باید `true` بمانند.

### ۳. ساخت دیتابیس اختصاصی

در **MySQL Databases** یا **Database Wizard**:

1. یک **دیتابیس جدید و خالی** بسازید؛ دیتابیس سایت دیگری را انتخاب نکنید.
2. یک کاربر با رمز قوی ایجاد کنید.
3. کاربر را به همین دیتابیس اضافه و **ALL PRIVILEGES** را برای آن فعال کنید.
4. نام کامل دیتابیس و کاربر، شامل پیشوند cPanel، را یادداشت کنید؛ مثل `account_dezhawo` و `account_storeuser`.

در **phpMyAdmin** همین دیتابیس را انتخاب کنید، به **Import** بروید و فایل `database/schema.sql` را وارد کنید. این فایل ساختار اولیه، نقش‌ها، تنظیمات ظاهر، تنظیمات روش‌های پرداخت و دو روش ارسال غیرفعال را می‌سازد؛ **مدیر، رمز پیش‌فرض یا محصول قابل فروش نمی‌سازد**. در صورت استفاده از زبانهٔ **SQL**، متن کامل همین فایل را کپی و اجرا کنید؛ فرمان ساخت دیتابیس را در دیتابیس مشترک یا سایت دیگری اجرا نکنید.

`schema.sql` مخصوص نصب اولیه است؛ آن را روی دیتابیس فعال فروشگاه دوباره وارد نکنید. برای شروع اختیاری می‌توانید `database/sample-products.sql` را یک‌بار وارد کنید. همهٔ محصولات نمونه **غیرفعال، با قیمت صفر و موجودی صفر** هستند و شناسهٔ رنگ‌ها مستقل است. برای فعال‌کردن هر نمونه، مشخصات، قیمت، هزینهٔ خرید و موجودی واقعی را ثبت کنید.

**اگر دیتابیس نسخهٔ قبلی دژاوو را دارید:** ابتدا از دیتابیس پشتیبان بگیرید، فایل‌های برنامه را جایگزین کنید و `app/config.php` و عکس‌های فعلی را حفظ کنید. وارد حساب مدیر اصلی شوید و در صورت نمایش اعلان بالای سایت، **«ارتقای دیتابیس»** را بزنید. نیازی به کپی و اجرای دستی کوئری ارتقا نیست. ارتقاها ستون‌های پرداخت و عکس و جدول دسته‌بندی‌ها را اضافه، محصولات قبلی را متصل و دسترسی مدیریت دسته‌ها را به مالک می‌دهند؛ کالاها، موجودی، سفارش‌ها و تنظیمات فعلی حفظ می‌شوند.

در نسخه‌های قدیمی که ساختار پرداخت یا عکس هنوز وجود ندارد، فروشگاه موقتاً در حالت به‌روزرسانی قرار می‌گیرد؛ فرم ورود مدیر فعال می‌ماند تا ارتقا را انجام دهد. نصب اولیه همچنان با ساخت دیتابیس و واردکردن `schema.sql` انجام می‌شود. روی نصب تازه با `schema.sql` فعلی، ارتقای جدا لازم نیست.

فایل‌های `database/upgrade-20261015-payment-methods.sql`، `database/upgrade-20261016-product-images.sql` و `database/upgrade-20261016-categories.sql` برای اجرای دستی و بازیابی هم در مخزن موجودند. ارتقای داخل سایت فقط مراحل ثبت‌شده در `app/DatabaseUpgrades.php` را اجرا می‌کند؛ برای افزودن تغییر ساختاری در نسخه‌های آینده، تشخیص و اجرای آن مرحله باید در همین فهرست ثبت شود. هر مرحله پس از بررسی ساختار واقعی اجرا می‌شود و اجرای مجدد، دسته‌های حذف‌شده توسط مدیر را بازنمی‌گرداند.

پوشهٔ `uploads/products` و فایل مخفی `.htaccess` داخل آن را همراه پروژه منتقل کنید. این پوشه باید برای کاربر PHP قابل نوشتن باشد؛ معمولاً سطح دسترسی `755` با مالک صحیح کافی است. هنگام به‌روزرسانی سایت، عکس‌های موجود داخل این پوشه را حفظ کنید. عکس‌های JPG، PNG و WebP تا **۸ مگابایت** پذیرفته می‌شوند؛ محدودیت ابعاد ۸۰۰۰ پیکسل در هر ضلع و مجموعاً ۲۴ مگاپیکسل است. فایل `.user.ini` تنظیمات مناسب حجم بارگذاری را دارد؛ اگر هاست تنظیمات اختصاصی دارد، مقادیر `upload_max_filesize=8M` و `post_max_size=12M` را در PHP Options یا MultiPHP INI Editor ثبت کنید و تنظیمات اختصاصی فعلی را حفظ کنید. تغییر `.user.ini` ممکن است با تأخیر در هاست اعمال شود. نصب GD، Composer یا نرم‌افزار جداگانه برای بارگذاری عکس لازم نیست.

### ۴. تنظیمات خصوصی

برای نصب آمادهٔ `dpsshop.ir`، فایل **`app/config.php`** از قبل موجود است و بخش دیتابیس و دامنه تکمیل شده‌اند؛ آن را با فایل نمونه جایگزین نکنید. اگر روی هاست قبلاً تنظیمات فعال دارید، فقط بخش `database` موردنیاز را منتقل کنید و کلیدهای برنامه و اطلاعات سرویس‌های فعلی را حفظ کنید.

برای نصب تازه با تنظیمات متفاوت، در File Manager از `app/config.example.php` کپی بگیرید و نام آن را **`app/config.php`** بگذارید. فایل حاوی اطلاعات اتصال خصوصی است؛ سطح دسترسی مخزن و فایل را خصوصی نگه دارید.

مقادیر را مطابق هاست تکمیل کنید:

| تنظیم | مقدار لازم |
|---|---|
| `app.env` | `production` |
| `app.base_url` | آدرس HTTPS واقعی سایت، همراه زیردایرکتوری اگر دارد، بدون اسلش آخر |
| `app.key` | کلید تصادفی مستقل برای امنیت برنامه |
| `app.installation_key` | کلید تصادفی مستقل برای نصب یک‌باره |
| `database.host` | معمولاً `localhost`؛ مطابق اطلاعات شرکت هاست |
| `database.port` | معمولاً `3306` |
| `database.name` و `database.user` | نام‌های کامل با پیشوند cPanel |
| `database.password` | رمز همان کاربر دیتابیس |
| `session.secure` | `true` |
| `sms.provider` | پیش‌فرض `niazpardaz`؛ برای حساب کاوه‌نگار `kavenegar` |
| `sms.niazpardaz_auth` | برای نیازپرداز: `api_key` یا `credentials` مطابق نوع دسترسی حساب |
| `sms.api_key` | کلید خصوصی نیازپرداز در حالت `api_key` یا کلید کاوه‌نگار |
| `sms.username` و `sms.password` | فقط در حالت `credentials` نیازپرداز؛ در حالت کلید API خالی بمانند |
| `sms.sender` | خط فرستندهٔ مجاز حساب انتخاب‌شده؛ برای ورود پیامکی لازم است |

**ورود موقت مالک:** در نسخهٔ خصوصی آماده، بخش `temporary_login` برای شماره و رمزی که مالک درخواست کرده تنظیم شده است؛ رمز خام داخل کد یا پاسخ عمومی قرار ندارد. اگر روی هاست `app/config.php` فعال دارید، فقط بخش `temporary_login` را از تنظیمات نسخهٔ جدید به آرایهٔ اصلی فایل فعلی اضافه کنید؛ اطلاعات دیتابیس، کلید برنامه و سرویس‌های فعلی را حفظ کنید. در فرم ورود، **«ورود موقت مدیر»** را بزنید، شماره و رمز تعیین‌شده را وارد کنید. اولین ورود موفق فقط همان شمارهٔ تنظیم‌شده را یک‌بار به‌عنوان مدیر آماده می‌کند و نصب را قفل می‌کند؛ بعداً ورود موقت، غیرفعال‌سازی حساب یا تغییر نقش را خنثی نمی‌کند. تلاش‌های ورود محدود و نشست موقت حداکثر هشت‌ساعته است.

پس از تأیید ارسال واقعی پیامک، `temporary_login.enabled` را در تنظیمات سرور `false` کنید. ورود موقت پنهان و نشست‌های آن باطل می‌شوند؛ همان حساب مدیر از روش پیامکی استفاده می‌کند. نسخهٔ نمونهٔ تنظیمات این روش را به‌صورت پیش‌فرض خاموش دارد. برای افزودن ورود موقت، انتخاب ویترین و سئو، مهاجرت جدید دیتابیس لازم نیست؛ دیتابیس باید ساختار عکس محصولاتِ نسخهٔ قبل را داشته باشد.

در صورت ساخت فایل تنظیمات تازه، هر کلید امنیتی را جداگانه با **۳۲ بایت تصادفی** تولید کنید؛ خروجی hex برابر ۶۴ نویسه است. نسخهٔ آماده کلیدهای مستقل دارد و نیازی به تولید مجدد نیست. اگر Terminal در cPanel فعال است، این فرمان را **دو بار** اجرا کنید:

```sh
php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'
```

خروجی اول را فقط در `app.key` و خروجی دوم را فقط در `app.installation_key` قرار دهید. کلید، رمز دیتابیس و اطلاعات سرویس‌ها را در گفتگو، فایل عمومی یا GitHub نفرستید. مقادیر نمونهٔ `CHANGE_TO_RANDOM_64_HEX` قابل استفاده نیستند.

### ۵. ساخت مدیر اصلی با نصب‌کنندهٔ پیامکی

آدرس `https://your-domain.example/install.php` را باز کنید؛ در نصب زیردایرکتوری، آدرس به `/shop/install.php` تغییر می‌کند.

اگر اولین ورود موقت مدیر موفق شده باشد، حساب مدیر و قفل نصب قبلاً ایجاد شده‌اند و اجرای نصب‌کننده لازم نیست. برای روش نصب با پیامک، کلید نصب، نام و شماره موبایل ایرانی مدیر را وارد کنید. **شماره باید در اختیار مالک فروشگاه باشد**؛ ورود پیامکی مدیر به دریافت پیامک روی همین شماره نیاز دارد. نصب‌کننده فرم CSRF و کلید نصب را بررسی و حساب مدیر را در تراکنش دیتابیس می‌سازد؛ در این مرحله رمز عبور ساخته نمی‌شود و حساب وارد سایت نمی‌شود.

پس از موفقیت، ساخت مجدد مدیر از نصب‌کننده مسدود است؛ تغییر فایل تنظیمات یا پاک‌کردن نشانگر نصب به‌تنهایی این قفل را باز نمی‌کند. **فایل `install.php` را از هاست حذف کنید.** در فروشگاه، «ورود / حساب کاربری» را بزنید و با همان شماره و کد تأیید پیامکی وارد شوید؛ دسترسی پنل مدیریت پس از شناسایی نقش مدیر ظاهر می‌شود.

### ۶. تنظیم پیامک و پرداخت

تنظیمات را فقط در `app/config.php` روی سرور ثبت کنید. نیازپرداز سرویس پیش‌فرض است و ارتباط مستقیم REST با PHP/cURL انجام می‌شود؛ نصب Composer یا پوشهٔ `vendor` لازم نیست.

**نیازپرداز با کلید API:** اگر پنل شما مانند نمونهٔ SDK کلید API می‌دهد، بخش `sms` را به این شکل تکمیل کنید. مقدارهای خالی باید با کلید خصوصی و خط مجاز همان حساب پر شوند:

```php
'sms' => [
    'provider' => 'niazpardaz',
    'niazpardaz_auth' => 'api_key',
    'api_key' => '',
    'sender' => '',
    'username' => '',
    'password' => '',
],
```

این حالت مطابق [SDK رسمی PHP نیازپرداز](https://github.com/NiazpardazSms/niazpardaz-sms-php) به `https://login.niazpardaz.ir/api/v2/RestWebApi/SendBatchSms` با هدر `X-API-Key` درخواست می‌فرستد.

**نیازپرداز با نام کاربری و رمز:** اگر دسترسی حساب شما مطابق مستندات REST با نام کاربری و رمز است، حالت را صریحاً تغییر دهید:

```php
'sms' => [
    'provider' => 'niazpardaz',
    'niazpardaz_auth' => 'credentials',
    'api_key' => '',
    'sender' => '',
    'username' => '',
    'password' => '',
],
```

در این حالت، نام کاربری و رمز خصوصی حساب را وارد کنید؛ درخواست JSON به `https://www.payamak.vip/api/v2/RestWebApi/SendBatchSms` ارسال می‌شود. برنامه نوع احراز هویت را خودکار عوض نمی‌کند؛ روش درست را بر اساس پنل و [مستندات نیازپرداز](https://niazpardaz-sms.com/webservice#document) انتخاب کنید.

کد تأیید در متن پیام با متد `SendBatchSms` ارسال می‌شود. متد `SendVoiceOtp` برای تماس صوتی است و در این اتصال استفاده نمی‌شود؛ ارسال پترن یا الگوی پیامکی در این نسخه پیاده‌سازی نشده است. خط فرستنده باید متعلق به حساب و مجاز باشد و حساب اعتبار کافی داشته باشد؛ شمارهٔ نمونهٔ مستندات مثل `10001234` خط آمادهٔ استفاده نیست. امکان ارسال به شماره‌های مسدودکنندهٔ پیامک تبلیغاتی و نیاز به تأیید متن یا خط خدماتی را از نیازپرداز بررسی کنید. پاسخ موفق API به معنای پذیرش درخواست ارسال است؛ تحویل واقعی را روی شمارهٔ خود و گزارش پنل بررسی کنید.

**کاوه‌نگار:** اتصال قبلی حفظ شده است. `sms.provider` را `kavenegar` قرار دهید و `sms.api_key` و `sms.sender` همان حساب را تنظیم کنید؛ `sms.niazpardaz_auth` در این حالت استفاده نمی‌شود. خط فرستنده باید مجاز و حساب دارای اعتبار باشد.

**زرین‌پال:** `payment.merchant_id` مربوط به درگاه همان دامنه را تنظیم کنید. برای فروش واقعی، `payment.sandbox` باید `false` باشد. مسیر بازگشت پرداخت `payment-callback.php` در آدرس `app.base_url` است.

**دیجی‌پی و خرید اقساطی:** در `app/config.php`، کلید `digipay` را داخل آرایهٔ موجود `payment` قرار دهید. کلیدهای زرین‌پال را حفظ کنید؛ دو آرایهٔ جدا با نام `payment` نسازید:

```php
'payment' => [
    'provider' => 'zarinpal',
    'merchant_id' => '',
    'sandbox' => false,
    'digipay' => [
        'username' => '',
        'password' => '',
        'client_id' => '',
        'client_secret' => '',
        'sandbox' => false,
        'seller_id' => '',
        'supplier_id' => '',
        'category_id' => '',
        'brand' => 'DEZHAWO',
        'product_type' => 1,
    ],
],
```

چهار مقدار احراز هویت دیجی‌پی و شناسه‌های واقعی فروشنده، تأمین‌کننده و دسته‌بندی مورد تأیید قرارداد را **فقط روی هاست** تکمیل کنید؛ شناسهٔ نمونه یا ساختگی وارد نکنید. برای محیط واقعی `payment.digipay.sandbox=false` است. نام کاربری، رمز و کلیدهایی که قبلاً در پیام یا تصویر منتشر شده‌اند را از پنل سرویس تعویض کنید و مقادیر تازه را در GitHub، SQL، تنظیمات عمومی پنل یا تیکت قرار ندهید.

دامنهٔ HTTPS و مسیر بازگشت `https://your-domain.example/digipay-callback.php` را برای پذیرنده در دیجی‌پی ثبت کنید؛ برای نصب `/shop`، همان پیشوند را در آدرس وارد کنید. این مسیر باید **POST عمومی از دیجی‌پی** را بپذیرد؛ آن را پشت ورود، محدودیت ارجاع یا قاعدهٔ فایروال مسدودکنندهٔ POST قرار ندهید. برنامه پرداخت را مستقل از نشست مرورگر و تنها پس از تأیید سمت سرور با مبلغ ریالی و شناسهٔ ذخیره‌شده ثبت می‌کند؛ دیدن صفحهٔ بازگشت یا ارسال رسید، تأیید پرداخت محسوب نمی‌شود. دسترسی خروجی هاست به دامنهٔ API محیط انتخاب‌شده و محدودیت IP پذیرنده را با دیجی‌پی بررسی کنید.

اتصال از درگاه یکپارچهٔ **UPG** استفاده می‌کند؛ نمایش و امکان انتخاب اعتبار یا اقساط تابع قرارداد فعال پذیرنده، نوع کالای مجاز و اعتبار مشتری در دیجی‌پی است. صرف واردکردن کلیدها، امکان اقساط برای همهٔ خریداران ایجاد نمی‌کند. پس از تکمیل تنظیمات و قرارداد، در **مدیریت → تنظیمات پرداخت** دیجی‌پی را روشن کنید. خاموش‌کردن آن، انتخاب برای سفارش‌های جدید و بنر اقساط را پنهان می‌کند؛ بازگشت تراکنش‌های قبلی همچنان بررسی می‌شود. بنر تبلیغاتی و دکمهٔ آن به انتخاب کالا و راهنمای خرید هدایت می‌کنند و وعدهٔ اعتبار قطعی نمی‌دهند.

بنر از [تصویر اصلی دیجی‌پی](https://www.mydigipay.com/mag/wp-content/uploads/2025/08/digipay-merchant-website-banner.jpg) استفاده می‌کند و در صورت خطای بارگذاری، همان متن را به‌صورت خوانا نشان می‌دهد. برای میزبانی محلی تصویر، فایل را با نام `assets/digipay-installments.jpg` قرار دهید؛ نسخهٔ محلی خودکار اولویت دارد.

**کارت‌به‌کارت / واریز بانکی:** در تنظیمات پرداخت، نام صاحب حساب و حداقل یک **شماره کارت معتبر یا شبای معتبر** وارد کنید؛ نام بانک و توضیح واریز اختیاری است. مدیر دارای `settings.edit` می‌تواند این مشخصات و کلید روشن/خاموش هر روش را تغییر دهد. اطلاعات حساب لازم برای واریز، هنگام ایجاد سفارش در همان سفارش ثبت می‌شود؛ تغییر بعدی حساب، مقصد سفارش قبلی را عوض نمی‌کند. مشتری پس از واریز، شماره پیگیری و توضیح را ثبت می‌کند. سفارش در وضعیت **در انتظار بررسی واریز** می‌ماند تا کاربر دارای هر دو مجوز `orders.edit` و `finance.view`، گردش واقعی حساب را بررسی و آن را تأیید یا رد کند. رسید متنی، پرداخت آنلاین یا تأیید خودکار نیست؛ مدت رزرو موجودی محدود است و تأیید دیرهنگام دوباره موجودی را کنترل می‌کند.

ورود پیامکی مدیر، کارکنان و مشتریان به سرویس پیامک فعال نیاز دارد. در دورهٔ راه‌اندازی، فقط شمارهٔ مالکِ تعیین‌شده در تنظیمات خصوصی می‌تواند از ورود موقت استفاده کند. انتخاب‌های پرداخت فقط پس از فعال‌سازی و تکمیل مشخصات همان روش نمایش داده می‌شوند. کارت‌به‌کارت به درگاه اینترنتی نیاز ندارد؛ فروش حضوری نقدی/کارت‌خوان نیز به درگاه وابسته نیست و از حساب مجاز مدیر یا کارمند ثبت می‌شود. پرداخت صرفاً با گزارش مشتری یا مشاهدهٔ صفحهٔ بازگشت تأیید نمی‌شود.

مقادیر `testing.otp_outbox` و `testing.payment_stub` روی هاست خالی/`false` بمانند. حالت production از مسیرهای آزمایشی استفاده نمی‌کند. ارتباط با سرویس‌ها با بررسی TLS انجام می‌شود؛ برای رفع خطا، بررسی گواهی را غیرفعال نکنید و مشکل CA یا دسترسی خروجی را با شرکت هاست حل کنید.

### ۷. آماده‌سازی فروشگاه

در پنل مدیریت:

1. محصولات واقعی و رنگ‌ها را ثبت کنید. هر رنگ موجودی مستقل در همان محصول دارد.
2. موجودی مغازه را شمارش و با دلیل مشخص ثبت کنید. از این پس **تمام فروش‌های حضوری را در بخش فروش حضوری ثبت کنید** تا موجودی سایت دقیق بماند.
3. روش‌های ارسال را تنظیم و فعال کنید. تیپاکس و چاپار در نصب اولیه غیرفعال هستند؛ هزینهٔ صفرِ نمونه را نرخ واقعی تلقی نکنید. گزینهٔ «پرداخت هنگام تحویل» فقط برای **کرایهٔ ارسال** است؛ هزینهٔ کالا از روش پرداخت انتخابی سفارش دریافت می‌شود.
4. هدر، منوها، فوتر، شماره تماس، آدرس، لینک‌های راهنما و لینک اعتبارسنجی اینماد را تنظیم کنید.
5. برای کارکنان نام، شماره موبایل و نقش مناسب ثبت کنید؛ تعیین رمز لازم نیست. کارکنان از همان فرم ورود و با پیامک شمارهٔ ثبت‌شده وارد می‌شوند. اگر شماره قبلاً حساب مشتری دارد، نقش همان حساب را تغییر دهید. نقش‌ها و مجوزها قابل مدیریت‌اند؛ مدیر اصلی و نقش پایهٔ مشتری حفاظت می‌شوند.
6. شرایط ارسال، مرجوعی و تحویل دیجیتال را با فعالیت واقعی مغازه هماهنگ کنید. محصولات دیجیتال در این نسخه با ثبت سفارش و **فعال‌سازی دستی** مدیریت می‌شوند.
7. روش‌های پرداخت را در تنظیمات پرداخت بررسی کنید؛ فقط روش‌های دارای حساب واقعی و شرایط نهایی‌شده را روشن کنید. برای واریز بانکی، مجوز بررسی مالی را فقط به افراد مسئول بدهید.
8. برای سفارش دیجی‌پی اعتباری/اقساطی، پس از **تحویل واقعی کالا** وضعیت تحویل را ثبت و گزینهٔ گزارش تحویل دیجی‌پی را اجرا کنید. این عمل به `orders.edit` نیاز دارد؛ نتیجهٔ گزارش در همان سفارش نمایش داده می‌شود و خطای ارسال قابل تلاش مجدد است. گزارش تحویل را صرفاً بعد از پرداخت ثبت نکنید.

## رفتار نسخهٔ فعلی

- فروشگاه فارسی و راست‌به‌چپ، انتخاب رنگ و قیمت وابسته به رنگ، سبد خرید سروری و سفارش فیزیکی/دیجیتال.
- انبار مشترک مغازه و سایت، ثبت فروش حضوری نقدی یا کارت‌خوان، اصلاح موجودی و گردش انبار. رزرو موقت و کنترل موجودی روی دیتابیس انجام می‌شوند تا فروش هم‌زمان موجودی منفی ایجاد نکند.
- ورود مشترک مدیر، کارکنان و مشتری با کد یک‌بارمصرف واقعی پیامکی، کنترل دسترسی سمت سرور بر اساس نقش حساب، و محافظت از آخرین مدیر اصلی فعال.
- ثبت و پاسخ **تیکت متنی**، سفارش‌ها و کد رهگیری، نقش‌ها، کاربران، روش‌های ارسال و تنظیمات هدر/فوتر/اینماد.
- پرداخت زرین‌پال و درگاه یکپارچهٔ دیجی‌پی با تأیید سمت سرور، واریز بانکی با بررسی مالی مدیر و کلید روشن/خاموش مستقل هر روش؛ بازگشت از درگاه یا ثبت شماره پیگیری به‌تنهایی سفارش را پرداخت‌شده نمی‌کند. وضعیت پرداخت و تحویل جداست.

اتصال خودکار به شرکت‌های حمل، صدور بارنامه، خرید خودکار تلگرام پریمیوم، آپلود پیوست تیکت و حسابداری کامل در این نسخه پیاده‌سازی نشده‌اند. لینک اینماد به اعتبارسنجی رسمی تنظیم می‌شود؛ دریافت مجوز اینماد باید جداگانه انجام شود.

## آزمون قبل از شروع فروش

ورود پیامکی واقعی مدیر، یک کارمند و یک مشتری را از فرم مشترک بررسی کنید؛ مشتری نباید به پنل مدیریت دسترسی داشته باشد. یک محصول واقعی با دو رنگ ایجاد کنید و نمایش قیمت/موجودی هر رنگ را بررسی کنید. یک فروش حضوری ثبت کنید و در مرورگر یا دستگاه دوم ببینید همان موجودی کاهش یافته است. با نقش فروشنده بررسی کنید بخش‌های بدون مجوز قابل استفاده نباشند. سپس سفارش اینترنتی، بازگشت پرداخت موفق و ناموفق، وضعیت سفارش، تیکت، روش ارسال و نمایش موبایل را بررسی کنید.

آزمون محلی با سرویس‌های آزمایشی جای تست حساب واقعی سرویس پیامک انتخاب‌شده، زرین‌پال و قرارداد دیجی‌پی روی دامنهٔ هاست را نمی‌گیرد. اتصال نیازپرداز و دیجی‌پی با شبیه‌سازی پاسخ سرویس قابل بررسی است؛ تحویل زندهٔ پیامک یا پرداخت واقعی بدون تکمیل حساب‌ها و شرایط پذیرندگی قابل تأیید نیست. یک سفارش واریز بانکی را نیز از ثبت شماره پیگیری تا تأیید/رد مالی و اثر آن بر موجودی بررسی کنید. تا انجام تست دامنه و سرویس‌ها، محصولات را برای فروش عمومی فعال نکنید.

## آزمون‌های توسعه روی سیستم محلی

این ابزارها فقط برای توسعه هستند؛ روی cPanel نصب Docker، Python، Node یا Playwright لازم نیست. راهنمای تکمیلی در `tests/README.md` است. آزمون‌ها داده ایجاد می‌کنند؛ آن‌ها را روی دیتابیس فروشگاه واقعی اجرا نکنید.

با Docker و Python 3، از ریشهٔ پروژه یک محیط **موقت و اختصاصی** راه‌اندازی کنید و آزمون‌های API/دیتابیس را اجرا کنید:

```sh
python3 tests/runtime.py start --private-dir /tmp/dezhawo-qa
python3 tests/integration.py --private-dir /tmp/dezhawo-qa
```

سرویس روی `http://127.0.0.1:8080` اجرا می‌شود. کلیدها، رمزهای آزمون و کدهای پیامکی تصادفی در مسیر خصوصی `/tmp/dezhawo-qa` خارج از پروژه می‌مانند. این ابزار دیتابیس `dezhawo_qa` را می‌سازد و SQL را فقط در دیتابیس خالی وارد می‌کند. آزمون integration آدرس خارج از loopback یا دیتابیس بدون پسوند `_qa` را نمی‌پذیرد. برای بررسی اجرای مجدد، داده‌های آزمون باقی می‌مانند؛ از آن‌ها برای فروش استفاده نکنید.

برای آزمون مرورگر، Node.js و یک Chromium نصب‌شده روی **سیستم توسعه** لازم است. وابستگی Playwright را خارج از مخزن نصب کنید؛ اگر مسیر Chromium متفاوت است، `CHROMIUM_PATH` را تغییر دهید:

```sh
npm install --prefix /tmp/dezhawo-browser-qa --no-audit --no-fund playwright
NODE_PATH=/tmp/dezhawo-browser-qa/node_modules \
CHROMIUM_PATH=/usr/bin/chromium \
DEZHAWO_QA_URL=http://127.0.0.1:8080 \
DEZHAWO_QA_SECRETS=/tmp/dezhawo-qa/secrets.json \
DEZHAWO_QA_OUTBOX=/tmp/dezhawo-qa/outbox \
node tests/browser.js
```

ابتدا integration را اجرا کنید تا مدیر و داده‌های مستقل آزمون آماده شوند. مرورگر ظاهر در چند اندازه، ورود، عملیات مدیریت، سبد، سفارش و تیکت را بررسی می‌کند. مسیرهای تنظیم‌شده برای secrets و outbox باید فقط مربوط به محیط خصوصی آزمایشی باشند.

پس از پایان، کانتینرهای آزمون را متوقف کنید:

```sh
python3 tests/runtime.py stop --private-dir /tmp/dezhawo-qa
```

توقف کانتینرها دیتابیس خصوصی آزمون را پاک نمی‌کند. اگر دیتابیس آزمایشی را با نسخهٔ قبلی همین توسعه ساخته‌اید، ساختار پیام‌های تیکت باید میکروثانیه را حفظ کند؛ به‌جای واردکردن مجدد کل schema، این تغییر محدود را **فقط در دیتابیس آزمایشی و پس از پشتیبان** اجرا کنید:

```sql
ALTER TABLE ticket_messages
  MODIFY created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6);
```

نصب اولیه از `database/schema.sql` فعلی این ساختار را دارد و به این دستور اضافه نیاز ندارد.

## فایل‌ها و دسترسی‌ها

- `index.php`: فروشگاه و پنل؛ `assets/`: ظاهر و کد مرورگر.
- `api.php`: ارتباط امن مرورگر با دیتابیس؛ `payment-callback.php`: تأیید زرین‌پال؛ `digipay-callback.php`: بازگشت POST و تأیید دیجی‌پی.
- `app/`: کد سمت سرور و تنظیمات خصوصی؛ `database/`: SQL نصب؛ `tests/`: آزمون‌های توسعه.
- `.htaccess`: انتخاب `index.php` و جلوگیری از دسترسی وب به `app/`، `database/`، `tests/` و فایل‌های خصوصی.

`.htaccess` و تنظیمات محافظتی داخل پوشه‌ها را حذف نکنید. هاست باید این قواعد را اعمال کند؛ URLهایی مثل `/app/config.php` و `/database/schema.sql` باید **403 یا 404** بدهند. اگر سرور قواعد Apache/LiteSpeed را پشتیبانی نمی‌کند، قبل از انتشار باید قواعد معادل توسط میزبان نصب شوند.

دسترسی رایج پوشه‌ها `755` و فایل‌ها `644` است. برای `app/config.php` در صورت سازگاری مالکیت هاست، `600` یا `640` مناسب است؛ PHP باید بتواند آن را بخواند. هیچ پوشه‌ای را `777` نکنید. اطلاعات خطای PHP باید در لاگ خصوصی هاست ثبت شوند؛ `display_errors` در production خاموش باشد.

## پشتیبان‌گیری و ارتقا

پیش از هر ارتقا از **دیتابیس** در phpMyAdmin به روش Export → SQL و از **فایل‌ها و app/config.php** در محل خصوصی پشتیبان بگیرید. نسخهٔ SQL حاوی اطلاعات خصوصی مشتریان است؛ آن را در `public_html` یا مخزن قرار ندهید. امکان بازیابی یک پشتیبان را در دیتابیس آزمایشی بررسی کنید.

برای ارتقای کد، ابتدا روی کپی آزمایشی بررسی کنید و هنگام انتقال، ثبت سفارش جدید را موقتاً متوقف کنید. فایل خصوصی `app/config.php` را نگه دارید؛ فقط فایل‌های برنامه را به‌روزرسانی کنید. **schema.sql را دوباره اجرا نکنید و دیتابیس را برای ارتقا پاک نکنید.** تغییر ساختار آینده باید با مهاجرت جداگانه و پشتیبان انجام شود.

برای ارتقا به ورود مشترک پیامکی، تغییر ساختار دیتابیس یا اجرای نصب‌کننده لازم نیست. شماره‌ها و نقش‌های فعلی حفظ می‌شوند و نشست‌های ورود قبلی باید دوباره با پیامک وارد شوند. رمزهای قدیمی و عملیات API با نام‌های `auth.adminLogin` و `user.password` دیگر برای ورود یا تنظیم رمز پشتیبانی نمی‌شوند. پیش از انتقال نسخه، سرویس پیامک و دسترسی مالک به شمارهٔ حساب مدیر را بررسی کنید.

برای افزودن اتصال نیازپرداز هم تغییر دیتابیس یا Import دوباره لازم نیست. فایل خصوصی `app/config.php` فعلی را حفظ و تنظیمات بخش پیامک را مطابق روش بالا تکمیل کنید. نصب‌های قبلی با `sms.provider='kavenegar'` می‌توانند همچنان از همان حساب استفاده کنند.

**ارتقای روش‌های پرداخت:** پس از پشتیبان‌گیری، برای دیتابیس موجود فقط `database/upgrade-20261015-payment-methods.sql` را اجرا کنید؛ سپس فایل‌های برنامه و ظاهر را کامل منتقل و آرایهٔ `payment.digipay` را به تنظیمات خصوصی فعلی اضافه کنید. `schema.sql` را روی فروشگاه موجود دوباره وارد نکنید، `app/config.php` را با نسخهٔ مثال جایگزین نکنید و نیازی به ساخت مجدد مدیر نیست. برای نصب تازه، فایل کامل `database/schema.sql` کافی است. شماره کارت و شبا از پنل مدیریت تنظیم می‌شوند و در فایل SQL نمونه وجود ندارند.

کلید `app.key` را در استفادهٔ عادی تغییر ندهید؛ تغییر آن کدهای ورود صادرشده را نامعتبر می‌کند. از دست‌دادن سیم‌کارت مدیر باید با فرایند خصوصی و احراز مالکیت روی هاست رسیدگی شود؛ دوباره اجرای نصب‌کننده یا ساخت رمز پیش‌فرض راه بازیابی نیست.

## رفع اشکال

| مشکل | بررسی |
|---|---|
| نصب‌کننده تنظیمات را آماده نمی‌داند | نام دقیق `app/config.php`، تکمیل دو کلید مستقل، نام‌های کامل دیتابیس و واردکردن SQL در همان دیتابیس |
| خطای اتصال دیتابیس | نام کاربر، رمز، host/port و اتصال کاربر با ALL PRIVILEGES به دیتابیس اختصاصی |
| خطای ۵۰۰ یا صفحهٔ خالی | نسخهٔ PHP، افزونه‌ها و Error Log خصوصی cPanel؛ متن خطا و کلیدهای محرمانه را عمومی منتشر نکنید |
| ورود یا session حفظ نمی‌شود | HTTPS، تنظیم `session.secure=true` و فعال‌بودن session در هاست |
| پیامک ارسال نمی‌شود | `sms.provider` و نوع احراز هویت نیازپرداز، کلید API یا نام کاربری/رمز همان روش، اعتبار حساب، خط `sender`، مجوز ارسال و دسترسی خروجی HTTPS هاست به سرویس انتخاب‌شده |
| سرویس ارسال را پذیرفته ولی کد نرسیده است | گزارش تحویل پنل، شمارهٔ مقصد، اعتبار و مجوز خط، محدودیت پیامک تبلیغاتی و تأیید متن یا خط خدماتی نزد سرویس‌دهنده |
| مدیر پس از ورود پنل ندارد | ورود با همان شمارهٔ ثبت‌شده برای مدیر، فعال‌بودن حساب و نقش/دسترسی آن؛ شمارهٔ جدید فقط مشتری می‌شود |
| روش پرداخت نمایش داده نمی‌شود | کلید روشن‌بودن همان روش در تنظیمات پرداخت؛ برای دیجی‌پی تکمیل شناسه‌ها و کلیدهای خصوصی، و برای واریز بانکی صاحب حساب و کارت/شبای معتبر |
| پرداخت آغاز یا تأیید نمی‌شود | مشخصات پذیرندهٔ همان سرویس، دامنه و base_url صحیح، HTTPS، مسیر بازگشت ثبت‌شده و دسترسی خروجی هاست؛ وضعیت سفارش را از پنل پیگیری کنید |
| دیجی‌پی گزینهٔ اقساط را نشان نمی‌دهد | فعال‌بودن اعتبار/BNPL در قرارداد پذیرنده، دستهٔ کالای مجاز و وضعیت اعتبار مشتری؛ تنظیمات UPG به‌تنهایی قرارداد اقساط ایجاد نمی‌کند |
| واریز بانکی هنوز پرداخت‌شده نیست | شماره پیگیری صرفاً برای بررسی است؛ مسئول دارای orders.edit و finance.view باید وصول واقعی وجه را بررسی و تأیید کند |
| گزارش تحویل دیجی‌پی خطا دارد | تحویل واقعی و وضعیت سفارش، نوع پرداخت اعتباری/اقساطی و پاسخ سرویس را بررسی و از دکمهٔ گزارش تحویل مجدداً اقدام کنید |
| موجودی مغازه با سایت فرق دارد | فروش حضوری خارج از سیستم، رنگ اشتباه، رزرو فعال، یا ورود/مرجوعی ثبت‌نشده |

اطلاعات دیتابیس و کلیدهای سرویس‌ها فقط در تنظیمات خصوصی هاست نگهداری می‌شوند. GitHub محل دریافت کد پروژه است؛ بارگذاری کد در GitHub به‌تنهایی سایت یا دیتابیس cPanel را راه‌اندازی نمی‌کند.
